A no-experience-required walkthrough

From folder to live site

You have an HTML file on your computer — maybe a fresh one, maybe a folder you've been picking at for weeks. By the end of this page it will be a real website with a real web address that you can text to anyone, and every future edit will publish itself automatically. Nothing here starts you over.

Free to follow ~30 minutes No terminal required Existing folders welcome

What you're actually setting up

Three things, each with one job. Almost every confusion beginners hit comes from mixing these up, so it's worth 60 seconds now.

Where you work Your folder A folder on your computer holding your index.html file. This is where you make changes.
→
The backup GitHub A free online copy of that folder. It keeps every version, so nothing is ever really lost.
→
The publisher Vercel Watches GitHub. The moment your folder changes there, it puts the new version on the internet.

You edit on the left. The site updates on the right. You never touch the right side again after today — that's the whole point of doing it this way instead of dragging files around.

Why not just drag and drop? You can, and it works for one afternoon. But then every edit means re-dragging, you have no history, and you can't undo a mistake. The setup below takes ten extra minutes once and then never asks anything of you again.

What you need first

Four accounts and apps. All free. Get these open in tabs before you start — chasing them mid-way is where people give up.

    The Claude desktop app — claude.ai/download

  • 02

    Free. Sign up with the email you actually check. Pick a username you don't mind appearing in web addresses — it may show up in your site's temporary URL.

  • 03
    GitHub Desktop — desktop.github.com

    A small app with buttons that does the GitHub part for you. This is what lets you skip the terminal entirely. Install it and sign in with the account from step 02.

  • 04

A portfolio, a wedding page, a recipe site, a club schedule — all fine. A site selling something, or a business's actual homepage, is meant to be on the Pro plan ($20/month). Start free; upgrade if and when money is involved.

Pre-flight for an existing folder

Four checks before the folder's contents leave your computer for the first time. The second one is the only one that can actually hurt you.

  • There's an index.html at the top level

    Not inside a src or pages subfolder, and not named home.html or Index.html. If your entry file has a different name, rename it now — this is the fix for the 404 you'd otherwise get later. (Framework projects are the exception: they build their own index.html, so leave them alone.)

  • No passwords or keys are in any file

    Look for .env, .env.local, or any file with an API key, database password, or token pasted into it. These must be listed in a .gitignore file before your first commit. Once a secret is pushed it stays in the repository's history even if you delete the file afterwards — so if you've already pushed one, go to wherever it came from and rotate it rather than just tidying up.

  • The junk is excluded

    node_modules, build output folders like dist, .next or build, and anything over about 50 MB. None of it belongs on GitHub — it's either rebuilt automatically or too big for the free tier. Same fix: list it in .gitignore.

  • Filenames are lowercase with no spaces

    Especially images. Your computer treats Beach Photo.JPG and beach-photo.jpg as the same file. Web servers do not, which is why images that worked locally vanish once the site is live.

All four are things Claude can do for you in one go, once it has access to the folder:

Say this to Claude

This folder is a website I've been working on and I'm about to put it on GitHub and Vercel for the first time. Check it for me: is there an index.html at the top level, are there any secrets or API keys in any file, is there anything huge or unnecessary that shouldn't be committed, and are any filenames going to break on a case-sensitive server? Write or update the .gitignore as needed, then tell me what you found and what you changed.

You will not lose your work. Nothing in this guide overwrites, moves, or deletes your existing files. GitHub adds a copy and a history; Vercel reads that copy. Your folder keeps working exactly as it does today.

The six steps

Do these in order. Each one ends with something you can see, so you always know whether it worked.

1
3 minutes · starting from scratch only

Make the folder and the file

Already have a folder with your work in it? Skip to step 2 — everything below is for building the very first file from nothing.

Create a new folder somewhere you'll remember — your Documents folder is fine. Name it something short with no spaces, like my-site. Inside it, create one file named exactly index.html.

Why that exact name? index.html is the one filename every web server in the world treats as "the front page." Call it home.html and visitors will get a "not found" error at your main address. This is the single most common first-timer mistake.

Here's a complete starting file. It's real, working HTML — nothing has been left out. Paste it in and change the words.

index.html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Jamie's Site</title>
  <style>
    body {
      font-family: system-ui, sans-serif;
      max-width: 640px;
      margin: 60px auto;
      padding: 0 20px;
      line-height: 1.6;
    }
    h1 { font-size: 40px; margin-bottom: 8px; }
  </style>
</head>
<body>
  <h1>Hello, I'm Jamie</h1>
  <p>This is my website. I made it myself.</p>
  <p><a href="mailto:you@example.com">Email me</a></p>
</body>
</html>

Check it worked: double-click index.html. It opens in your browser and looks like a web page. The address bar will start with file:// — that means only you can see it. That's what the rest of this guide fixes.

2
2 minutes

Hand the folder to Claude

Open the Claude desktop app and give it access to your project folder — the new one from step 1, or the one you've been working in all along. Look for the + or Add folder control near the message box and point it there.

From now on you describe what you want in plain English and Claude edits the files directly. You don't need to know any HTML — but you do need to be specific about what you want.

If the folder already has work in it, start by asking Claude what's there rather than asking for a change. It costs you one message and saves you from asking for something the site already does.

Say this to Claude — existing folder

Give me a tour of this folder: which file is the homepage, what other pages exist, and what each file is for. Then tell me the three things you'd improve first. Don't change anything yet.

Then, for a change:

Say this to Claude

I have an index.html file in this folder. It's my personal site. Please redesign it: dark background, a big heading with my name, three short sections — About, Projects, Contact — and make it look good on a phone. Keep everything in the one file. Show me the file when you're done.

After it edits, double-click index.html again (or refresh the tab if it's still open) to see the change.

The one habit worth building. Ask for one change at a time and look at the result before asking for the next. Ten small requests beat one giant one, because when something goes wrong you know exactly which change caused it.

3
5 minutes

Put the folder on GitHub

Existing folder? Do the pre-flight checks above before this step — particularly the one about secrets. This is the moment your files leave your computer, and it's much easier to exclude a file now than to scrub it out of the history later.

Open GitHub Desktop. Then:

  1. File → Add Local Repository, and choose your my-site folder.
  2. It will say the folder isn't a repository yet and offer to create a repository here. Click that.
  3. Leave the name as my-site. Ignore the other options. Click Create Repository.
  4. In the left panel you'll see index.html listed as a change. In the box at the bottom left, type a short note — first version — and click Commit to main.
  5. Click the big Publish repository button at the top. Untick "Keep this code private" if you want, or leave it ticked — either works with Vercel. Click Publish repository.

Your folder now exists on github.com. That's it — that's what GitHub is.

If the folder was already a repository — you've used git with it before, or it contains a hidden .git folder — GitHub Desktop will simply adopt it at step 1 above and show you its existing history. Skip straight to committing anything uncommitted, then publish or push. If it's already on github.com too, you're done with this step entirely: go to step 4.

Two words you'll keep seeing. Commit means "save a labelled snapshot of my folder." Push means "send my snapshots up to GitHub." In GitHub Desktop these are the two buttons at the bottom left and top of the window, and you'll press them in that order forever.

Check it worked: go to github.com, click your profile picture, then Your repositories. my-site is listed, and clicking it shows your index.html.

4
2 minutes

Point Vercel at it

This is the step where your site goes live, and it's shorter than the last one. If your project is already on your Vercel dashboard, it's done — go to step 5.

  1. Go to vercel.com and sign in with GitHub.
  2. Click Add New… → Project.
  3. You'll see a list of your GitHub repositories. Find my-site and click Import. If it isn't listed, click Adjust GitHub App Permissions and grant access to that repository.
  4. Vercel will show a settings screen with a Framework Preset dropdown. For a plain HTML file, leave everything alone — the correct answer to every question is the default. For a project with a package.json, Vercel will have already detected the framework and filled in the build command; accept what it detected rather than typing your own.
  5. Click Deploy.

Wait about thirty seconds. You'll get a confetti screen and a web address ending in .vercel.app.

Your site is live. Open that address on your phone. Send it to someone. It's on the real internet, on real HTTPS (the padlock), served fast from servers around the world — and it cost nothing.

5
Forever after

Learn the loop

This is the payoff, and it's the only routine you need to remember from here on:

Ask Claude for a change → Look at the file → Commit in GitHub Desktop → Push → Live in ~30s

Nobody has to tell Vercel anything. It watches your GitHub repository and rebuilds the site every time you push. In GitHub Desktop the push button is labelled Push origin and sits at the top of the window right after you commit.

Two things Vercel does for you quietly that are worth knowing about:

  • Instant rollback. If you publish something broken, open your project on vercel.com, find the previous deployment in the list, and use its menu to promote it back to production. Your old site returns immediately.
  • Every version is kept. Each push gets its own permanent preview address, so you can always look at what the site was two weeks ago.

The free-tier ceiling. Hobby allows 100 deployments per day and 100 GB of traffic per month. For a personal site, both numbers are effectively unreachable. If you somehow blow past them, Vercel pauses the site rather than charging you.

6
Optional · 10 minutes + ~$12/year

Use your own domain name

The .vercel.app address works permanently. But if you want jamie.com instead:

  1. Buy the name from a registrar — Namecheap, Cloudflare, Porkbun, or Vercel itself. Expect $10–$15 a year for a .com.
  2. In your Vercel project: Settings → Domains → Add, and type the domain you bought.
  3. Vercel shows you two or three DNS records — rows with a Type, a Name, and a Value. Copy them into the DNS settings page at the place you bought the domain.
  4. Wait. Usually minutes, occasionally a few hours. Vercel turns the domain green when it's working and sets up the HTTPS certificate itself.

If the DNS records screen looks like nonsense, screenshot it and hand it to Claude — this is a genuinely fiddly step and it's a good one to have help with.

Say this to Claude

I bought a domain at Namecheap and I'm adding it to my Vercel project. Here's a screenshot of the DNS records Vercel is asking for, and a screenshot of Namecheap's DNS page. Tell me exactly what to type into which box.

Four prompts worth keeping

When something looks wrong

The heading on my page is overlapping the paragraph below it on my phone but looks fine on my laptop. Here's a screenshot. Fix it in index.html and tell me in one sentence what was wrong.

When a deploy fails

My latest Vercel deployment failed. Check the build log for my project, explain the error in plain language, and fix the file.

Adding a second page

Add a second page called about.html with the same styling as index.html, and put a simple navigation bar at the top of both pages linking them together.

Understanding your own site

Walk me through my index.html section by section and explain what each part does, as if I've never seen HTML before. Don't change anything.

Say what it should look like, not how to code it. "Make the buttons look like the ones on Stripe's site — rounded, subtle shadow, they lift slightly on hover" gets you a much better result than "add CSS to the buttons." You're the art director, not the engineer.

Do you need a database?

Almost certainly not yet. A plain HTML site can do a startling amount. Before adding Supabase, answer these four questions honestly.

1Does something a visitor types need to still be there when a different visitor arrives later?
2Do people need to log in as themselves and see their own stuff?
3Does the content change without you editing the file — user posts, sign-ups, bookings, uploads?
4Do you need to look at what visitors submitted, in a list, later?

All four are no → skip this section entirely. Your site is done. A portfolio, a menu, a résumé, an event page, a link page, a documentation site — none of these need a database. Editing the file and pushing is your content management system.

Any one is yes → you need somewhere to store things between visits, and Supabase is the friendliest option. Read on.

The common middle case. "I just want a contact form." You don't need a database for that. Use a form service like Formspree or Tally — you paste one line into your HTML and submissions arrive in your email. Reach for Supabase when you need to query the data, not just receive it.

If the answer was yes: Supabase in five moves

Supabase gives you a real database with a web address you can talk to from your HTML page's JavaScript. The free tier is generous and needs no credit card.

  1. Create a project at supabase.com. Pick a region near your visitors. Save the database password it generates somewhere safe — you won't need it for this, but you'll want it later.
  2. Create a table. Use the Table Editor, or just ask Claude with the Supabase connector attached. Make sure Row Level Security is enabled — Supabase turns it on by default and you should leave it on.
  3. Write the security policies. This is the part that actually matters, and the part to lean on Claude for. Policies decide who can read and write which rows. Without them your table is either invisible or wide open.
  4. Get your two values from Project Settings → API: the Project URL, and the key beginning sb_publishable_.
  5. Add the code to your page, below.
Inside your index.html, before </body>
<script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2"></script>
<script>
  // Both of these are safe to have in your public HTML.
  const db = supabase.createClient(
    'https://YOUR-PROJECT.supabase.co',
    'sb_publishable_YOUR_KEY_HERE'
  );

  // Save something
  async function signGuestbook(name, message) {
    const { error } = await db
      .from('guestbook')
      .insert({ name: name, message: message });
    if (error) console.error(error.message);
  }

  // Read it back
  async function loadGuestbook() {
    const { data, error } = await db
      .from('guestbook')
      .select('*')
      .order('created_at', { ascending: false });
    if (error) return console.error(error.message);
    console.log(data);
  }
</script>

The one security rule you must not get wrong. Supabase gives you two kinds of key. The publishable key (sb_publishable_…) is designed to sit in public HTML — anyone can read it, and that's fine, because your Row Level Security policies are what actually protect the data. The secret key (sb_secret_…) ignores every policy. It must never, ever appear in a file you push to GitHub. If you paste one into your page by accident, go to Supabase and rotate it immediately.

Say this to Claude

I want a guestbook on my site: visitors can leave a name and a message, and everyone can read all the messages, but nobody can edit or delete anyone else's. Create the table in my Supabase project, write the Row Level Security policies, and then add the form and the display code to my index.html. Explain the security policies to me in plain language when you're done.

Free projects go to sleep. A Supabase project with no database activity for about a week gets paused, and you resume it with one click in the dashboard. Fine for a hobby project; if a site needs to be reliably awake, that's the reason to move to the $25/month Pro plan.

When it doesn't work

Five things go wrong for nearly everyone. Here they are with their fixes.

What you seeWhat it meansFix
404 on your live site No file named index.html at the top level of the repository. Check the spelling and check it isn't inside a subfolder.
Your edit isn't showing up You committed but didn't push, or you pushed and haven't waited. Check for a Push origin button in GitHub Desktop. Then check the Deployments list on vercel.com.
Your repository isn't listed in Vercel Vercel's GitHub app doesn't have permission for it. On the import screen, click Adjust GitHub App Permissions and grant access.
Build fails on an existing project Usually a missing environment variable — a key that lives in your local .env file, which correctly never got committed. Add it in Vercel under Settings → Environment Variables, then redeploy.
The push is enormous or won't finish node_modules or a build folder is being committed. Add them to .gitignore, then ask Claude to remove them from the commit before you push.
Images don't load once live Capitalisation. Your computer treats Photo.JPG and photo.jpg as the same file; the web server does not. Make every filename lowercase with no spaces, and match it exactly in your HTML.
Custom domain stuck on "Invalid Configuration" The DNS records aren't right yet, or haven't propagated. Re-check each record character by character, then give it a few hours before assuming it's broken.

The words, translated

Repository (repo)
Your project folder, plus its full history. That's all.
Commit
Saving a labelled snapshot of the folder. Like naming a save file.
Push
Uploading your snapshots to GitHub.
Main
The default version of your project. What's on main is what's on your live site.
Deploy
Vercel taking your files and putting them on the internet. Happens by itself.
Production
The real, public version — the one at your actual address.
Preview
A private test address for a version that isn't live yet.
DNS
The internet's address book. It's what connects a domain name you bought to the servers holding your site.
Row Level Security
A Supabase feature that decides, row by row, who's allowed to see or change what.
